# DUSTBOUND 0.5.2 · 加载与运行顿挫优化

基于上一轮 0.5.1 的 2D 版本，保留玩法、数值、美术图集和存档格式。本轮针对可从代码确认的开销点优化，不把它们直接等同于你电脑卡顿的唯一原因。

## 直接试新版

1. Roblox Studio 打开 **Dustbound-0.5.2.rbxlx**，按 **F5 / Play**。
2. 先观察加载页，再进入标准远征，比较第一批敌人出现、清场后整备、打开经营台时的顿挫。
3. 游戏内按 **F6** 显示 / 隐藏悬浮诊断。不想用快捷键，可在「设置 → 运行诊断」下方点击「显示 / 隐藏悬浮诊断」。
4. 诊断开启后可以继续远征，不会自动暂停。
5. 如果仍然一卡一卡，请在**正在卡顿时**截取悬浮诊断；再告知是 Studio Play 还是发布后的 Roblox 客户端，以及当时位于加载、战斗、经营台还是整备。

如果 Studio 自身快捷键截获 F6，请使用设置中的按钮。

## 改了什么

### 1. 加载不再集中堵住一帧

- 先让独立加载页有机会绘制，再读取共享模块和图集数据。
- 旧版约 **119,179 段 RLE** 一次生成整张图的字符串表，再拼接约 4 MiB RGBA 字符串并转成 buffer。
- 新版每批最多 **32 行 / 128 KiB RGBA 字符串**，分批写入同一张 EditableImage；批次间让出 Heartbeat，长批次还有约 3ms 的协作式检查点。
- 仍然只使用一张 1024×1024 高清图集，没有把原画缩小或偷偷换成低清图。
- 测试逐字节验证新解码结果与旧解码结果完全相同。
- 图像 API 不可用时，保留原有 GUI 兼容绘制；启动阶段的长矩形构造循环也分批让出时间。

**这主要是把开销摊到多帧，改善加载页响应，不保证总加载时长更短。** 32 次分帧等待在 60Hz 下本身就有约半秒的调度时间；底层模块解析、图像分配与引擎纹理上传仍可能有不可拆分开销。

### 2. 加载进度与首帧交接

- 加载条来自代码实际阶段，不再随经过的秒数自行涨到 92%。
- 显示图集解码、界面构建、对象准备、等待战局等具体阶段。
- 收到网络数据不再立刻宣称可玩；等待客户端完成绘制回调交接后才隐藏加载页。
- 加载完成后断开加载页的逐帧轮询；后续客户端 / 服务端错误仍通过属性事件重新展示诊断。
- 进度条是**工作阶段权重**，不是磁盘或网络下载百分比，也不是预计剩余时间。

### 3. 去掉周期性界面重建

- 经营台不再随计时每半秒销毁和重建整页控件。
- 保留控件、滚动位置和按钮，只更新货物、建议、能源状态等文字。
- 按钮处理器读取最新状态，避免控件复用后仍操作旧的能源分配。
- 设置中的性能读数也原位刷新，不重建设置页。
- 网络消息只更新最新快照；完整 HUD 绘制集中到 RenderStepped，避免同一帧从两个入口重复刷新。
- 本地操作、阶段变化和请求确认优先刷新；常规 HUD 限频，文字未变化时不重复赋值。
- 尺寸检测限频，尺寸不变就不重复设置缩放和重建布局。

### 4. 减少首次出现与持续动画开销

- 加载阶段预先准备 **2 个普通虫体、1 个重甲虫体、2 台机器人、8 个图形特效和 8 个文字特效**，之后由现有对象池复用。
- 只是少量预备，不一次创建最大规模战场；战况超过储备时仍可能按需创建对象。
- 主菜单、暂停等静止状态不再每帧重复更新隐藏 / 冻结的战斗动画。
- 移动和弹丸仍随渲染帧更新；复杂腿部姿态常规约 30Hz，轻量动效约 15Hz 更新，降低高刷新率显示器上的重复属性写入。
- 调整表现层时钟，避免新快照到达时把动画时间往回拨。
- 机器人按服务端周期做短时间位置预测，但**不预测或授予矿料**。
- 布局重建时显式清理脱离界面的旧对象池。

服务端模拟步长仍为 **0.1 秒**，快照间隔仍为 **0.15 秒**；未通过降低战斗模拟频率来换性能。

## 离线对比结果

同一套当前 mock、相同操作流程，运行 600 次渲染回调和 10 秒模拟时间；基线源代码取自上一轮交付的 0.5.1 包。

| 场景 | 指标 | 0.5.1 | 0.5.2 |
|---|---|---:|---:|
| 主菜单静置 | 属性赋值次数 | 12,725 | 1,473 |
| 打开经营台采矿 | 实例创建 / 销毁 | 343 / 340 | 1 / 0 |
| 打开经营台采矿 | 属性赋值次数 | 33,452 | 21,321 |
| 暂停界面 | 属性赋值次数 | 12,850 | 1,578 |
| 早期战斗 | 实例创建次数 | 113 | 3 |
| 早期战斗 | 属性赋值次数 | 51,681 | 28,145 |

**这些是离线操作次数，不是实机 FPS、CPU 耗时、GPU 开销或内存峰值。** 预热把部分创建从战斗移到了加载阶段，所以战斗中的创建下降不代表整局从未创建这些对象。样本是固定早期场景，不代表最大敌群压力。

原始记录：`docs/validation-0.5.2/operations-before.json` 与 `operations-after.json`。

复现新版：

```sh
python tools/performance_probe.py
```

对比旧源码（使用当前测试 mock）：

```sh
python tools/performance_probe.py --source-root /路径/到/0.5.1工程
```

## 如何读悬浮诊断

- **FPS / P95 / 最慢帧**：最近最多 180 个本机渲染回调间隔。FPS 是该窗口的平均值，P95 更适合观察频繁顿挫。
- **>50ms 帧累计**：这次运行中超过 50ms 的回调间隔次数；切到后台、拖动窗口等也可能计入，并不全是游戏代码导致。
- **最近快照**：距离最后收到状态包的时间，**不是 ping / RTT**。不要把正常 0.15 秒的快照节奏当作丢包。
- **本脚本帧回调峰值**：最近采样周期内客户端 RenderStepped 回调的最大墙钟耗时；不包含全部 Roblox 引擎、GPU、其他脚本和网络回调开销。
- **面板重建 / 布局**：本次客户端运行的累计次数。长期停留在同一经营台时，面板重建不应继续周期性增长。
- **客户端准备 / 图集**：本客户端代码的准备时间和图集初始化时间；不是 Studio 打开工程所花时间。
- **embedded / asset / fallback**：内嵌图集、上传图集、GUI 兼容绘制。`fallback` 的实例数更多，是进一步排查的重要线索。

如果仍卡，可以先开「轻量动效」并关闭「伤害数字」做对照；这不是要求你长期牺牲画质。若 FPS / P95 明显差，但本脚本回调耗时很低，还应检查引擎渲染、兼容绘制、Studio 编辑器开销及其他程序，不能直接断定为网络问题。

## 验证与边界

- **161 项 pytest 通过**，包含上一轮回归和本轮新增 22 项加载 / 运行优化测试。
- **17 个顶层 Luau 脚本编译通过**。
- **8,000 条原生 Luau 属性断言通过**。
- 三波教学、标准十波与追加十二波的固定策略数值路线通过。
- Rojo 构建成功，测试逐一核对 Place 中 17 个脚本 Source 与当前源码。
- 本轮没有改变 Core、Rules、科技成本、奖励公式或存档 schema。

**尚未在你的电脑或 Roblox Studio / 真实客户端中测得帧率提升。** mock 的 Heartbeat 等待是确定性的测试替代，不模拟实际调度，也不证明真实帧预算已经达标。图像 API 权限、GPU 上传、首次声音加载、Studio 双端运行及真实网络仍需要实机检查。

默认 `AtlasImageId = 0`，本次主要优化的是这条内嵌图集路径。自定义上传图集和音频仍可能受下载 / 权限影响；没有通过预加载全部远程资源来无限拖长启动。
