# DUSTBOUND 0.7：全量检查与修复报告

日期：2026-09-17  
审计对象：工作区当前 0.7 集成源码；不是 GitHub 新版本。  
修复构建：`Dustbound-0.7.0-AUDIT.rbxlx`。**仍是测试工程，不是全量回归通过的正式版。**

## 一、结论

基础系统已有可运行的分层，不需要推倒重写。本轮发现的主要问题来自 **0.6 → 0.7 接入不完整**：新规则与旧入口/配置并存、客户端重复推算价格、部分状态没有同步清理，以及逐帧/逐次资源变化触发不必要的 UI 工作。

已修复明确复现的逻辑错误，补上当前入口的回归测试，减少运行包与界面更新开销。

但目前不能宣布项目“无明显问题”或“可以上线”：全量测试仍有 **129 项失败**。其中有大量旧规则/旧 UI 断言，也存在尚未恢复的交互、显示选项与诊断能力。必须迁移验证或修复，不能把它们整体忽略。

本轮没有改变 2D 基础风格、免费武器/遗物节奏、三种局外资源、四项采矿投资或新手缓冲原则。

## 二、已修复的逻辑问题

| 问题 | 影响 | 修复 |
|---|---|---|
| 放弃远征只清空外层机器人，RunSystems 内仍保留 | 下一次 snapshot 将机器人重新带回菜单状态 | 同时清理 run.robots、offer、pause 状态 |
| 畸形 node 参数被 `and/or` 默认值转换成第 1 关 | false / 缺失 node 没有按无效请求拒绝 | 显式取值并校验，不隐式开局 |
| 三选一暂停期间仍能调用投资接口 | UI 和服务器的“选择期间暂停”规则不一致 | Core 与 RunSystems 同时拒绝投资，选择和重抽保持可用 |
| 付费重抽扣了金矿，支出账本未更新 | 钱包与 ledger 不一致 | 从 run.spent 同步账本，保持金矿守恒 |
| 永久机器人加成使实际数量提前封顶，UI 仍显示可买 | 可点击但服务器拒绝、价格状态误导 | Core 输出权威 prices，UI 不再单独推算机器人上限 |
| 磁轨穿透按无限射线筛选、按敌人数组顺序取前三 | 可伤到射程外目标；穿透顺序与空间位置不符 | 限制投影距离到武器射程，按距离排序取前三 |
| 迫击炮描述优先高耐久，代码却选最近敌人 | 武器策略描述与真实行为冲突 | 在射程内选择最高当前耐久目标 |
| 暂停时三选一仍覆盖暂停界面 | 选择按钮无效，缺少清晰的恢复入口 | 暂停/设置优先于选择层，恢复后继续原 offer |
| 云档读取失败没有当前客户端的重试/访客入口 | 正确阻止云写入，但玩家无法从 UI 恢复 | 增加重试读取、明确不保存的访客确认；锁丢失提示重新加入 |
| 终极天赋退款没有纳入立即保存触发项 | 可能要等自动保存，退出异常时有丢失风险 | refund_talent 成功后触发保存 |
| 服务器拒绝/超时消息被下一帧提示覆盖 | 点击无效时用户不知道原因 | 临时反馈保持四秒；服务器 actionResult 可见 |
| 客户端在真正渲染前就上报 ui_ready | 加载统计提前，掩盖尚未绘制的界面 | 绘制后再经下一帧交接，上报真实就绪阶段 |
| first_robot_deposit 指标没有发出 | 采矿漏斗统计失真 | 首次实际返航入账时记录一次 |
| 波次报告填的是累计击杀与 0 伤害占位 | 调试/平衡分析依据不真实 | 每波独立统计击杀、有效伤害、承伤和主要输出武器 |
| 图鉴把 `ammo` 等逻辑图标 ID 当成真实图集切片 | 打开图鉴直接报 Unknown sprite；高清和降级模式均复现 | 明确映射到存在的切片；保留未知资源断言防止静默掩盖 |
| 已有 confirmReroll 设置未接入新版界面 | 付费重抽缺少约定的确认 | 付费重抽显示确认；保留 token 检查，取消不扣金矿 |
| 功能研究按旧 unlock 效果分类，然后才替换成数值效果 | 纯伤害研究被标成功能解锁，蓝图名称也误导 | 按最终 effects 分类；数值增幅与机器人/连锁/重抽功能区分，并修正名称 |

新增审计用例见 `tests/test_audit_07.py`。原 `tests/test_integration_07.py` 的 18 种波次数量、免费选择、矿运、五武器位等专项仍通过。

音效/音乐音量按钮和保存失败重试入口也已接回当前设置页。未配置音乐资源时，调节音乐音量不会凭空播放音乐。

## 三、架构检查与本轮优化

### 当前运行路径

```text
独立 Boot.client：加载屏、错误显示，不依赖游戏 Core/云档
        ↓
Runtime：统一组装 Config + Catalog + Tech + Economy
        ├─ Server → Core（权威战斗、行为校验、结算）
        │             └─ RunSystems（采矿、武器/遗物选择、局内账本）
        │          → ProfileStore（云档锁、重试、幂等快照）
        │          → Telemetry（有界日志）
        └─ Client → UI / BattleView → WeaponRig / Animation
                   Art（共享图集、分块解码、兼容降级）
                   Audio（客户端音效）
```

**适合保留的设计**
- 金矿、伤害、抽取验证、研究消费和结算均由服务器负责，不信任客户端发来的金额。
- Core/Rules/RunSystems 仍可脱离 Roblox 执行单元测试与 Luau CLI 检查。
- 云档读取失败不生成可写的空云档；存档锁、重试快照和幂等写入已有独立实现。
- 独立加载屏、共享图集、战斗对象池、有界 FX 和日志方向正确。

**本轮已实施**
1. 新增唯一 Roblox 组装入口 `Runtime.lua`，去掉 Server/Client 两份依赖初始化，减少“客户端拿原始 Tech、服务器拿转换后 Tech”的风险。
2. 统一发布后的 prices 契约；当前可操作投资列表由配置给出，旧投资不再混进当前快照价格。
3. 刷怪持续时间/敌人数上限与 Core 使用同一 Config 值，修正旧 28 秒配置与实际 24 秒的冲突。
4. 从 Rojo 运行包移除未使用的 `Panels / Motion / TechMap / Gallery / GalleryData`，但保留源码供旧回归与后续迁移参考。不是删除旧测试来制造通过率。
5. 增加只装载“实际发布模块”的页面测试，避免测试环境有旧模块而发布包漏依赖。
6. 构建后核对所有嵌入脚本与工作区源码逐字一致；22 个嵌入脚本通过。

**后续值得做，但本轮没有冒险大改**
- Core 同时维护 `s.stage/s.ore/s.robots` 与 `s.run.phase/gold/robots`。sync 是当前桥接层，也是本次残留机器人 bug 的来源。建议未来改为单一 run 状态源，快照只做投影。
- Client 仍包含页面布局与网络交互，约两百多行密集逻辑；可按“前哨/研究/选择/设置”拆页面模块，但应先建立等价 UI 测试，避免又一次整体重写丢功能。
- Economy 仍是对旧 Catalog/Tech 的适配器。长期应生成一份最终的 0.7 配置，明确将旧配置限定为迁移工具，而不是无限叠加 patch。
- 敌人出现条件、矿点几何仍有硬编码。若后续扩展敌人/星球，应先建立数据化 roster/world 配置，不必现在增加 ECS 或第三方框架。

## 四、加载与运行效率

### 可核验结果

| 测量 | 修复前 | 修复后 | 解释 |
|---|---:|---:|---|
| Place XML 文件大小 | 1,837,474 字节 | 907,427 字节 | 减少约 50.6%；主要移除未用 GalleryData 等。不是网络下载时间减少 50.6% |
| 菜单空闲 180 渲染帧：GUI 属性写入 | 1,260 | 0 | 停止隐藏战斗更新，状态不变不重复赋值 |
| 投资页 20 次金矿变化：新建 GUI 对象 | 600 | 0 | 保留控件，原位更新价格/可购买状态 |
| 同上：销毁 GUI 对象 | 600 | 0 | 避免资源变化造成重复布局与垃圾回收 |
| 高清图集解码写入次数 | 32 | 32 | 分块解码保留，后续复用同一张图集 |
| 降级绘图启动让帧次数 | 7 | 14 | 更细颗粒让帧，降低长同步构造风险；不代表总加载时间缩短 |

数据来自实际 Lua 在 mock 下的操作计数，日志在 `audit-0.7/performance.json`。工具同时记录 Python/Lupa 总耗时，但**不拿它当 Roblox 启动时长或帧率**。前后使用同一测试库存；真实发布包另做瘦身验证。

### 加载判断

- **高清路径的实现基本合理**：共享图集、32 行分块解码、独立加载屏；未发现反复解码同一图集的路径。
- **兼容降级仍偏重**：测试库存启动约 1,832 个实例，对照高清约 203 个；大量矩形拼图不是低端手机理想方案。让帧只能改善响应，不能消除实例成本。
- 图鉴改为每页最多六张卡，避免一次构建全部 21 个条目，尤其减轻降级绘图成本。
- 战斗敌人和 FX 使用对象池；离线预算测试没有替代高波次实机内存与 P95 帧时检查。

发布前建议上传正式 atlas 图片并配置 `AtlasImageId`，在真实发布环境验证权限/加载失败回退；同时用 Studio MicroProfiler 和一台低端移动设备测启动、首个敌人生成、图鉴切页、20 波战场与长时间运行。

## 六、仍明显存在的冲突与发布阻塞

1. **新旧测试契约并存。** 旧测试仍要求开局副武器、临时补给、击杀金矿、旧教学结算、线性科技/旧按钮等。不能回滚用户确认的新设计去满足它们；也不能一刀切跳过。必须逐条重建当前规则下的等价保障。
2. **设置与能力不完全对齐。** 旧 profile 仍保留 damageNumbers、screenShake、showTips、compactNumbers 等字段，新 BattleView/界面尚未全部消费；诊断面板/F6 等旧 QoL 没有全部恢复。本轮没有假称这些选项已生效。
3. **研究与图鉴可用性仍需提升。** 网络已不是六条必经直线，但缩放/快速定位、跨区替代路线提示、触屏节点尺寸需要真实交互检查。图鉴已修复崩溃，但不是旧版大幅插画表现的完全替代。
4. **后期强度仍偏稳。** 自动策略能无资源注入顺序通完 24 关，不代表取舍和平衡已经合理；要对比不投资、偏采矿、偏战斗、不同武器组合的失败率，且不可牺牲新手缓冲。
5. **快照仍含兼容字段和重复数据。** 每次同步带 profile/报告等，目前规模有界，但多人真实网络和序列化成本未测；建议先测量再分为静态/动态包，不急着增加复杂增量协议。
6. **真实云与存档迁移尚未验收。** 默认云档关闭。即使 mock 下锁/幂等通过，也必须在已发布测试体验验证多服抢锁、离线重连和 schema 7 数据。

## 七、建议下一步顺序

1. 用当前入口逐项接替 129 个失败测试，并优先恢复确实承诺过的交互保障；不要先扩大内容。
2. Studio 实测该 AUDIT 构建，验证实际 RemoteEvent、EditableImage/上传图集、移动端可读性、音效和云档失败恢复。
3. 基于实机数据再做快照拆分/降级绘图 LOD；基于对照策略再调后期难度。
4. 上述通过后再整理正式 0.7 发布包。本轮审计构建不替换 0.6.1 回退包。
